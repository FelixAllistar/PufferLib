Retro environment review and training strategy — 2026-09-07

Historical review of the pre-change code. The subsequent user-authorized
implementation and measured results are in `REALIGNMENT_20260907.md`.

Recommendation: make execution of the original ROM the training contract. Keep
QuickNES as the current candidate implementation, validate it against an
independent reference, and optimize shared immutable data, observation work,
and batching. The native-C SMB port currently does not meet the requested
exactness requirement. Moving training to it and checking whether a policy
transfers is a different acceptance criterion from preserving ROM behavior.

This is a review, not an implementation change. The environment, configuration,
existing modifications, and running trainer were left in place. Findings refer
to `/home/felix/puffertank/pufferlib`, which is the actual Git repository. There
is also an older `ocean/retro` outside that repository in the workspace root.

Observed configuration: `config/retro.ini` selects `quicknes`, empty
`spawn_levels`, 8,192 agents, four workers, and frameskip four. The running
process inspected during review explicitly overrides this with
`./puffer train retro env.backend=fast base.load_model_path=latest
base.checkpoint_interval=25`. Its effective historical settings beyond those
arguments were not independently recovered.

Findings, ordered by impact:

1. **P1: All-level training is broken in the native vector path.**
   `retro.h:933` assigns each seed before `puf_init`, which clears the entire
   environment at line 494. `retro_pick_spawn` at line 360 applies xorshift
   directly to that zero seed; zero remains zero forever. The apparent fix in
   `src/pufferl.cu:2416` is inside the generic initialization branch and is
   bypassed by retro's `MY_VEC_INIT`. A fresh-source diagnostic constructing
   four environments with `spawn_levels=all` produced `rng=0 spawn=0` for all
   four. Correct initialization must preserve or assign distinct nonzero
   seeds in retro's actual constructor path. Verify coverage through that
   path, not only through the standalone chaos tool, which reseeds itself.

2. **P1: QuickNES's level boot changes the label without selecting the stage.**
   `retro.h:636` writes WorldNumber `$075F` and LevelNumber `$075C`, but does
   not select the corresponding AreaNumber `$0760`. The diagnostic booted all
   32 requested starts. Every stage within a world had the same area number,
   area pointer, and level-data pointer as that world's first stage. For
   example, requests `1-1` through `1-4` all yielded AreaNumber zero and data
   pointer `$A690`; `8-1` through `8-4` all yielded `$AA01`. Labels alone pass
   the current implementation's checks. The local port's
   `src/smbcore/common.c:18` illustrates why area indices also need to account
   for intermission areas; `area.c:1770` actually selects data using WorldNumber
   and AreaNumber. Furthermore, `retro.h:671` only consults the level cache
   when `spawn_n > 1`: the diagnostic requesting only `8-4` reset into `1-1`.
   The fast reset has the same single-entry condition (`retro_fast.h:619`),
   and fast initialization assumes CSV entry zero is 1-1 (`retro.h:568`).
   Build and verify a real start-state bank before enabling all-level training.

3. **P1: The current backends and wrapper do not preserve every ROM trajectory.**
   `retro_fast.h:23` explicitly records an input-phase mismatch. Local patches
   cap game loops, change death completion, and turn some original hangs into
   silence while continuing the episode (`smb_patches/noise_silence.patch`,
   `music_timeout.patch`, `loop_caps.patch`). These are observable changes in
   exactly the unusual states a glitch-preserving environment must retain.
   Even the QuickNES wrapper writes `$000E=6` and executes an extra neutral
   frame during some deaths (`retro.h:772`); this extra frame is not included
   in `tick`. Both wrappers end an episode after one unchanged game frame
   counter, and hard-code a 4,000-frame limit. An episode limit is a valid
   training choice, but it is not a ROM death. Separate emulation from task
   termination: no gameplay RAM writes after restoring a start state; record
   external truncations separately. A game spinning in its own CPU loop need
   not freeze a cycle-budgeted emulator's host worker.

4. **P1: QuickNES reset observations do not belong to the restored state.**
   `retro.h:701` and `:818` load a snapshot and immediately read `frame()`.
   `Nes_Emu.cpp:231` restores emulation state without restoring the host frame
   pixels or frame palette. A freshly initialized emulator returned a null
   frame pointer. After moving Mario from x=40 to x=123, reset restored x=40
   while the framebuffer hash remained `c445773c`, the old image. The
   thread-local framebuffer is also reused by other environments, so the
   initial image can depend on which environment rendered last. Store a
   matching initial observation, or image and palette, alongside each start
   state. Do not silently advance the game a frame just to obtain an image.
   The lazy level cache also publishes its pointer before construction is
   complete, has no synchronization, and keys entries by CSV position rather
   than actual level identity (`retro.h:670`). Fixing seeds can expose this
   previously hidden concurrent first-use race. Prebuild the immutable bank
   before worker threads start.

5. **P1: Completion detection and flag reward are incorrect.**
   `retro_obs.h:48` scans `$16..$1A` for types `$2D/$31`. The local game source
   puts the flagpole in actor slot 5, `$1B`, with type `$30`
   (`src/smbcore/area.c:1469`, `consts.h:57`). A synthetic state with that
   flagpole and player state 3 is not detected. Separately, both reward calls
   use `flag_now && !env->has_flag` after synchronizing `env->has_flag` to
   `flag_now` (`retro.h:782,798`, `retro_fast.h:819,833`); the expression is
   always false. Use validated game completion transitions and a before/after
   event edge. For preserving flagpole glitches, touching the pole should not
   automatically end emulation before the subsequent behavior can occur.

6. **P2: Rewards and reported return do not measure clearing levels reliably.**
   `config/retro.ini:55` disables multi-level spawning. Lines 56–62 give score
   a weight of 0.05, kills 1, no death penalty, no flag/area reward, and idle
   penalty 0.01. A 100-point event pays 5; a 10-pixel step contributes at most
   about 0.0029 potential shaping. This strongly prioritizes collecting score
   over the requested completion objective. The idle penalty exceeds that
   progress signal and can make ending an episode attractive. The kill
   detector (`retro_obs.h:77`) treats ID zero as vacant even though zero is a
   green Koopa; disappearance is not a reliable kill event. Episode return
   only accumulates the final step reward (`retro.h:804`,
   `retro_fast.h:839`). The shaping invariance claim is also unsupported by
   the implementation: area transitions omit the potential difference, and
   true terminal transitions do not use zero terminal potential. Matching
   gamma alone does not repair either boundary. Use completion as the main
   task reward, log actual episode sums and per-level results, and make
   auxiliary score/kill rewards optional.

7. **P2: The action interface excludes original control sequences.**
   The twelve masks at `retro.h:63` omit combinations including left+B,
   left+A+B, and stationary A+B. Fixed four-frame holds exclude arbitrary
   one-frame press/release timing. The ROM's physics can remain unchanged
   while these restrictions make some glitches inaccessible to the policy.
   Provide an exact one-frame raw-controller interface for replay and
   validation; expose the required combinations for training. Frameskip four
   can remain an explicitly restricted training experiment. Variable action
   durations must account for elapsed emulated time in discounting.

8. **P2: The parity command cannot certify exactness.**
   `retro.c:376` checks only nine scalar fields for fast self-consistency.
   Cross-backend checks allow up to 5% engine/stat mismatches, do not include
   the reported X drift in the pass condition, and do not compare observations
   (`retro.c:385–402`). The test also deliberately avoids the production clone
   path because it has an acknowledged extra neutral frame (`retro.c:337`,
   `retro_fast.h:452`). A PASS is not frame/RAM parity, nor coverage of all
   levels and glitches. Use exact comparisons for optimized versus reference
   builds of the same core; use corresponding game state and canonical video
   at aligned controller sampling points across independent emulators.

What the extra components actually do:

| Component | Current use | Recommended treatment |
| --- | --- | --- |
| `nes_emu/` | Direct ROM execution, compiled into retro | Keep the emulation machinery needed by this ROM |
| `retro_fast.h`, fetched SMB port, patches | Unconditionally built; active only for `backend=fast` | Remove from the default training build; retain separately if useful for experiments |
| SMB2J objects | Built alongside SMB1 by `build.sh:342` | Unneeded in an SMB1 ROM-only target |
| `cores/*.so`, `include/libretro.h` | Not loaded by the active wrapper; `core_path` is only copied | Optional independent reference tooling |
| `retro.cu.bak.gpu`, `.bak.proclite` | Historical code, outside the active build | Archive for clarity; removing files alone will not increase SPS |
| `gravity`, `max_vx`, `jump_v`, `run_accel`, `friction` | Parsed and stored, unused by the ROM physics | Remove misleading configuration fields |
| Heartbeat, signals, watchdog recovery | Fast-backend machinery | Keep out of the ROM-only training target |

The fast backend is also larger than its introductory comments suggest:
`SMB_state` contains 64 KiB address space, 8 KiB graphics ROM, and 16 KiB PPU
memory per environment, plus pointers/metadata. `fast_arena_alloc` additionally
allocates an approximately 18 KiB reset snapshot per environment. The source
ROM file is read once, but PRG/CHR bytes are copied into each state's storage.
This is not an approximately 18 KiB total environment.

Recommended implementation order:

1. Establish an explicit ROM identity and reference contract. The reviewed
   file's SHA-256 is
   `ec299b990e8bfee8ba46e3f61d63b2e1ae5b8a2e431de84e2e4bbd692dc53586`.
   Record core version/build, mapper, region, and controller timing. An
   explicitly supplied missing ROM must fail, rather than silently selecting
   another file from the current fallback list (`retro.h:130`). QuickNES is
   a candidate, not automatically a hardware-perfect reference.
2. Fix the vector seeds, state-bank construction, reset observations, reward
   events, and metrics. Prepare starts for all 32 stages, with matching
   observations and verified loaded geometry/data. Prefer states obtained
   through verified ROM play; a validated level-select setup can seed the
   bank, but its reset distribution should be explicit. Add hard-mode or
   alternate starts separately when wanted. Secrets and wrong warps should
   emerge through ROM execution, not a hand-written transition table.
3. Make the default build ROM-only. Preserve original CPU, PPU, and APU
   timing, even when no host audio is produced. The current QuickNES instance
   already uses `silent_buffer`; removing game music logic is not a valid
   headless optimization.
4. Optimize immutable graphics and observation processing first. Each
   QuickNES PPU currently allocates and decodes the same read-only CHR cache
   (`Nes_Ppu_Impl.cpp:89`). For this 8 KiB CHR ROM, normal/flipped decoded
   caches total 16 KiB per environment: approximately 128 MiB across 8,192
   environments. Share that cache with explicit immutable ownership.
   `retro_compute_obs_real` currently performs 9,216 palette-to-luma
   conversions per observation. A per-frame palette-to-luma lookup can reduce
   this work while retaining the same sampling and summation order. Resolve
   the full palette slot correctly; current `pix & 63` differs from the
   preview's full-index lookup. Verify observations before and after changes.
5. Benchmark thread count, environment count, buffering, and policy cost
   after correctness fixes. Use actual rollout actions and resets across all
   levels; the current bench repeats RIGHT from the same start and excludes
   initialization. Measure emulated frames/s, decisions/s, total learner SPS,
   reset cost, memory, and per-level success separately. Start comparisons
   around 512/1024/2048 environments and 1/2/4 workers, keeping learner batch
   semantics comparable. These are experiment points, not measured optima.
   There was an active CPU-heavy trainer during review, so no clean peak-SPS
   estimate or promised speedup is supplied.

Acceptance must cover full-render versus skipped-render execution, save/load
round trips, worker-count independence, every start state, pipes/vines,
underwater levels, castle loops, death/respawn, level transitions, and known
glitch input tapes. Compare complete relevant emulator state for changes
within one core, and compare observations/rewards/terminal boundaries as well
as RAM. A RAM-only check can miss a broken policy input. Finite regression
tests provide evidence for the covered behavior; they cannot prove every
possible ROM trajectory is identical.

Diagnostic source and executables from this review are isolated at
`/tmp/retro-review-aM06bI/`. The initial probe compiled the current source with
Clang -O2 and ran 4,000 identical per-frame random inputs through full-render
and three-skip/one-render QuickNES instances. RAM matched after every frame;
109 of 1,000 observed whole-buffer comparisons differed. The follow-up compiled
at -O0 and repeated the test, resolving visible palette colors and invoking
the actual observation builder: zero visible pixel-index differences, zero
palette-resolved image differences, zero policy-observation differences, and
zero RAM differences. Thus the whole-buffer differences were outside the
visible image. This supports retaining skip-render mode for the tested tape;
it is not an all-level, full-emulator-state, or hardware-parity certification.

Upstream context: [SMB Vanilla's own README](https://github.com/nukep/smb-vanilla-port)
describes a gameplay reconstruction intended to support most non-gamebreaking
glitches, not execution of the original CPU program. This supports keeping
that port's compatibility goal separate from the exact ROM execution contract.
