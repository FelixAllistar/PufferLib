This document proposes the next benchmark milestone. Only the three-task pilot is implemented. Environment execution stays stock CPU Bend; neural inference/training stays native C/CUDA. The pilot becomes a regression screener, not the main benchmark.

Current priorities and implementation status are maintained in [TODO.md](TODO.md). MiniWoB parity comes first; text encoding is a parallel investigation, with frozen static embeddings now the first semantic candidate. The following architectural options are proposals, not mandatory prerequisites for the first ports.

Current policy and limitations

The observation is 128 public words: a 32-byte instruction region, five fixed 16-word node records, and padding. Nodes contain role, geometry, checked/focus/enabled flags, a one-character name, and up to two input characters. Each word becomes five floats: value/255 and four equality indicators for a–d. A learned linear 640-to-128 projection feeds two 128-wide MinGRU layers, followed by action/value outputs. There is no tokenizer, learned text embedding table, pretrained language model, variable-node encoder, or general text output. The a–d indicators are hand-engineered pilot features.

Slots have separate input positions and action outputs. Label order varies only by cyclic rotation, not all permutations. This architecture does not enforce the same matching rule at every node. Current evaluation establishes success on a tiny finite family, not language or website generalization. A stalled watcher episode could involve wait, typing into an unfocused input, or repeated actions; exact diagnosis requires the episode/action trace. Checkbox failures are measured, but order sensitivity has not been isolated experimentally.

Proposed policy contract

Encode instruction text and each node's accessible name/value with shared text weights. Begin with a byte embedding table and a small ordered sequence encoder, preserving exact strings and numbers. An embedding is a trainable vector lookup; it does not confer English understanding. Compare small pretrained text features separately if paraphrase/general-language transfer becomes a requirement. Count their compute, memory, and any pretraining or demonstrations.

Combine each node's text vector with role, state, geometry, and parent/label relationships. Apply one shared node scorer conditioned on the instruction, page context, and recurrent history. Add bounded attention for comparisons and relationships. Start with an explicit node budget (for example 128); record truncation and provide scrolling/page traversal rather than silently dropping the target. Pool contextual nodes for the recurrent memory and value head.

Factor actions into operation, observed target node, and text payload. Support click, focus/type, select, scroll, back, and submit through the same public contract in both backends. Start text entry with copying spans from the instruction or visible page, then add generated bytes/tokens. Never expose the private goal record as input or offer answer-filled action candidates. Copying exact text does not solve paraphrases or generated responses. Keep coordinate/pixel evaluation separate from element-targeted evaluation.

Proposed benchmark ladder

| Level | Content | What it measures |
| --- | --- | --- |
| Screener | Existing widgets plus arbitrary permutations, words, distractors, menus and forms | Grounding, editing, focus, basic memory and simulator conformance |
| Static site collections | Multi-page documentation, directories, news/product catalogs | Link traversal, reading tables, searching/filtering, selecting evidence or answers |
| Stateful local applications | Catalog/cart, inbox, issue tracker, booking form | Multi-step work, persistence, recovery and final-state correctness |
| External evaluation | Selected original MiniWoB tasks, WebShop, then WebArena/WorkArena | Transfer beyond our own generator and transition model |

A static site collection is still interactive through links and forms, but workflows that alter carts, messages, or reservations require explicit application state. Merely displaying realistic HTML is insufficient.

Start with two concrete families: a shopping catalog inspired by common retail interfaces and a documentation/help center. Suggested tasks are selecting the least expensive in-stock item matching attributes, selecting a size and adding it to a cart, finding a version-specific installation page, and locating a requested table entry. Add inbox/ticket workflows after the shared navigation and text contract works. These are proposed tasks, not present capabilities.

For each family, define records, routes, public views, legal interactions and success predicates. Bend computes transitions and a bounded public view. A real HTML/CSS/JavaScript application independently exercises the same task specification in Chromium. Match its extracted public observations and resulting state against Bend on sampled action traces, including mistakes and recovery. Shared specifications simplify authoring but can share bugs; retain independent invariants and external task tests. Screenshots are initially Chromium-only and are not required for DOM training.

An arbitrary downloaded site does not compile into this simulator. Unmodeled JavaScript, server behavior and browser layout require real browser execution or an explicitly implemented model. Bend's generated C is the simulator implementation, not a C-to-JavaScript conversion of Chrome.

Data generation and evaluation

Generate independent variations of content, widget structure, navigation graph, instructions and visual layout. Include distractors, reordered fields, duplicate names, unavailable products, empty results and invalid input paths. Require generated tasks to be solvable; use scripted solvers for generator validation, with demonstrations reported separately if used for learning. Imported product/document data and DOM snapshots can improve realism, but a recorded trace does not define outcomes for arbitrary alternative actions.

Freeze splits before tuning: unseen records/strings; unseen layout templates; unseen workflow combinations; and an independently implemented site family. Color/font changes alone do not test DOM-policy transfer. Existing pilot evaluation seeds have already been used during development and are not an untouched test set.

Report per-family success, worst-family performance, actions, invalid/no-op actions, timeout causes, simulator/browser disagreements, throughput, wall time to target success, and variation over training seeds. Compare equal actions and equal wall time. For external benchmarks preserve their scoring and identify changed interfaces; a rewritten task suite is a separate benchmark. Do not claim a browser-training speedup from comparing batched Bend simulation with sequential browser evaluation.

Immediate implementation order: (1) pinned original-MiniWoB oracle, task specifications, typed Bend primitives and a versioned variable-node/text contract; (2) first task ports and a measured frozen-text-feature investigation; (3) catalog/documentation site families with held-out content/layout tests; (4) broader site-derived workflows and mixed real/simulated training. Improve the existing checkbox task as an encoder diagnostic rather than spending the whole project tuning a four-letter toy.

Mind2Web's original dataset provides recorded demonstrations/snapshots; treat it as grounding/data support rather than a complete counterfactual RL simulator.
